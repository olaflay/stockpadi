# Scaffold Log

What exists in this repo as of the initial scaffold, why, and what's still a stub. Read `AGENTS.md` first for the locked decisions this scaffold follows; this file is the record of how those decisions became code.

## Stack as built

Next.js 16 (App Router, Turbopack for dev), React 19, TypeScript strict mode, Tailwind CSS v4 (CSS-first config, no `tailwind.config.js`). Dexie 4 over IndexedDB for local-first storage. Supabase JS client pointed at a Supabase Cloud project (no URL/keys committed), deployed on Vercel. Serwist (Workbox successor) for the service worker. Vitest + fake-indexeddb for tests. lucide-react for icons (emoji icons are banned by `.agents/rules/zero-ai-slop-design.md`).

## Data layer

**`src/lib/db.ts`** — the local IndexedDB schema. Mirrors the server shape deliberately: `products` and `customers` are business-wide (no branch column on the row, matching the Postgres table), `businessProfile` and `branches` are singleton/small tables for offline settings access, and there is **no stored `stock` or `creditBalance` field anywhere**. Both are always computed:
- `src/features/inventory/stock.ts` — `getCurrentStock(productId, branchId)` sums `stockMovements`.
- `src/features/customers/credit.ts` — `getCustomerCreditBalance(customerId)` sums `customerCreditMovements`.

This is the one rule the codebase treats as non-negotiable (`.agents/rules/offline-sync-and-ledger.md`), so it's enforced structurally, not just by convention: there is no code path that writes a stock or balance total directly.

**`supabase/migrations/20260807054724_init_schema.sql`** — full Postgres schema: `business_profile`, `branches`, `users`/`roles`, catalog tables, `stock_movements` (append-only ledger) with `inventory_stock` as a `security_invoker` view over it, `customer_credit_movements` with `customer_credit_balances` as a view, `sales`/`sale_items` (immutable, void is a separate column), `purchases`/`purchase_items`/`suppliers`, `expenses`, `receipts`, `audit_logs`, `devices`. Every ledger table carries a unique `client_id` as the sync idempotency key.

**`supabase/migrations/20260807054734_rls_policies.sql`** — role-based RLS per the permission matrix in `.agents/rules/database-and-rls.md`. Branch-scoped roles (cashier, inventory_staff) are restricted via a `user_branches` join; unrestricted roles (owner, manager, accountant, admin) see across branches. **Flagged in the migration's own header comment**: the PRD's "Limited" permission for Manager on expenses/audit-log was undefined, so this migration states an explicit interpretation (insert+select but no delete; no visibility into role-change/PIN-reset audit entries) rather than guessing silently. Confirm before this reads as locked.

Not yet done: these migrations still need to be applied against the linked Supabase Cloud project. Run `npx supabase login`, `npx supabase link --project-ref <ref>`, then `npx supabase db push`; no local Docker stack is part of this deployment workflow.

## Config layer (reusability boundary)

Per `.agents/rules/reusability-and-multi-client.md`, three things stay out of feature code:
- **`src/config/business-types.ts`** — the four PRD templates (Grocery, Pharmacy, Electronics, General Retail) as data, not `if (businessType === ...)` branches. Onboarding reads this list directly.
- **`src/config/branding.ts`** — business name, accent color, logo URL read from `NEXT_PUBLIC_*` env vars, with the accent color injected as a CSS variable in `src/app/layout.tsx`.
- **Credentials** — `.env.example` documents every var; nothing real is committed (`.env*` stays gitignored except the example file itself).

## Design system

**`src/styles/tokens.css`** — Samsung One UI as the lead system (thumb-reach layout, focus-block radii), Meta's data-lite/accessibility discipline borrowed for contrast and low-end-device legibility. Extended (by a later pass) with M3-style tonal container color pairs for status chips/toasts, state-layer opacity tokens, and a two-step motion scale, still structured as CSS custom properties only, wired into Tailwind v4's `@theme inline` block in `src/app/globals.css`. No hardcoded hex/px in component code — everything reads `var(--color-*)`, `var(--radius-*)`, `var(--font-size-*)`.

## PWA / offline

**`next.config.ts`** wraps the config with `@serwist/next`. **`src/app/sw.ts`** precaches the app shell (via `@serwist/next/worker`'s `defaultCache`) and registers a `BackgroundSyncPlugin` on `/functions/v1/sync-push` with a 24h retention window, matching the "needs attention after 24h" threshold in PRD §10.1. Disabled in dev (Turbopack doesn't support Serwist yet — a warning prints in dev but the build isn't blocked). `public/manifest.json` + `public/icon.svg` (placeholder "S" mark — swap for real branding assets).

## Screens and shared state primitives

Every primary screen (`.agents/skills/scaffold-new-screen.md`) is built against eight shared components in `src/components/ui/`: `OfflineBanner`, `SyncIndicator`, `Skeleton`, `EmptyState`, `NoResultsState`, `ErrorState`, `PermissionDenied`, `Toast`/`ToastProvider` (now with `neutral`/`success`/`warning`/`danger` tone variants reading the same container tokens `ErrorState` uses). `OfflineBanner`'s connectivity check (`src/lib/use-online-status.ts`) uses `useSyncExternalStore` specifically to avoid a server/client hydration mismatch on `navigator.onLine` — the first version used `useState` + `useEffect` and broke hydration in testing; this was caught and fixed during the build, see "Verification" below.

Screens built:
- **`/onboarding`** — step 1 of the 3-screen-max onboarding: business name + business-type picker, writes `businessProfile` and seeds default `categories` from the template.
- **`/dashboard`** — per-branch/consolidated toggle, today's sales total, low-stock count (computed live from the ledger, threshold in `use-dashboard-metrics.ts`), unsynced-changes banner.
- **`/products`** and **`/products/new`** — search/list with SKU+barcode+name matching, role-gated add flow (owner/manager/inventory_staff/admin).
- **`/pos`** — real checkout: product search → cart → payment-method tag → `completeSale()` writes the sale, its stock movements, and one outbox entry inside a single Dexie transaction.
- **`/reports`** — period toggle (today/week/month), best sellers, low stock. Inventory Staff gets a reduced low-stock-only view (same flagged "Limited" interpretation as the RLS migration, stated inline in the component).
- **`/settings`** — business profile display, branch management (add up to 6), role-gated to owner/admin.
- **`src/app/page.tsx`** — root route reads local `businessProfile` and routes to `/onboarding` or `/dashboard`, no network round trip.

**`src/features/auth/use-current-user.ts`** is the single choke point every screen reads a role through — now backed by `AuthProvider`/`CurrentUserContext`, which resolves the cached session and local user before any authenticated screen renders. Real Supabase Auth + PIN login is implemented (`src/features/auth/session.ts`, `device-id.ts`, `pin-hash.ts`, `assert-permission.ts`, `manage-staff-client.ts`), backed by the `manage-staff` Edge Function.

## Testing

`vitest.config.mts` + `vitest.setup.ts` (imports `fake-indexeddb/auto` so Dexie works under Node). **`src/features/inventory/__tests__/sync-conflicts.test.ts`** is the mandatory two-device concurrent-write test named in `.agents/skills/write-offline-conflict-test.md`: seeds a stock ledger, simulates two devices independently selling the same last unit, asserts both sales survive in either sync order, and asserts a retried sync of the same movement doesn't double-count. Backed by a new small piece of production logic, **`src/features/inventory/merge-stock-movements.ts`** (`mergeIncomingStockMovements`), which dedupes incoming movements by `clientId` before inserting — this is real code the sync-pull path will need, not test-only scaffolding.

## Verification performed

- `npm run build`, `npm run lint`, `npm run test` all pass clean as of the last change.
- Full manual walkthrough in-browser: onboarding → add branch → add product → complete a sale → confirmed Dashboard and Reports both reflect the new sale and the resulting negative/low stock correctly, live (no reload needed, via `dexie-react-hooks`' `useLiveQuery`).
- Exercised the offline banner (forced `navigator.onLine = false`) and the permission-denied state (temporarily forced the stub user to `cashier`) directly in the browser, not just read from code.

## Known gaps / next steps

1. Placeholder icon/branding assets.
2. The two "Limited" permission interpretations (Manager on expenses/audit-log, Inventory Staff on reports) are explicit guesses, flagged in code comments, not confirmed decisions.
3. RLS on `stock_movements`, `sales`, `sale_items`, and `customer_credit_movements` still permits direct PostgREST writes by role alone, bypassing the `sync_apply_*` RPCs that are the only place price/ledger integrity is enforced — flagged in a 2026-08-08 security review, tracked as a fix in progress.

Since the initial scaffold: real auth (Supabase Auth + PIN login, see "Data layer" above) is implemented, migrations now include four additional `sync_apply_*` functions beyond the original two files, and the `sync-push`/`manage-staff` Edge Functions exist under `supabase/functions/`.

**Auth and routing additions (2026-08-08):**
- `/login` — email and password sign-in. On mount, checks IndexedDB for existing local users; if any exist, redirects to `/unlock` immediately so returning users never see the email form. Loading skeleton is shown during the IndexedDB check to prevent a flash of the wrong screen.
- `/register` — new store account creation. Two-zone layout: illustration header (top viewing area) + scrollable form (bottom interaction area). Business type chips use `aria-pressed` and named icons (lucide-react: Store, Pill, Cpu, Package). Redirects to `/unlock` after creating the first local user.
- `/unlock` — multi-user picker and PIN entry. Replaces the former single-user unlock. Shows a layout-matching skeleton while IndexedDB hydrates. Auto-selects if only one user exists. Submits automatically when the 4th PIN digit is typed. Role badge uses tonal token pairs from `tokens.css`. "Switch user" link only renders when there are two or more users.
- `BottomNav` — navigation tabs are filtered at runtime from the authenticated user's role: cashier sees Sell only; inventory_staff sees Products only; owner/manager/admin/accountant see Dashboard, Reports, Settings, and their role-appropriate items. Filtering is client-side from the cached local user record with no added latency.
- `session.ts` — PIN session expiry reduced from 30 days to 24 hours, matching the daily-shift authentication pattern in a retail environment.
- All three auth screens comply with the `zero-ai-slop-design.md` checklist: lead system named in component JSDoc comment, all tokens read from `tokens.css` (no hardcoded hex or px), shape applied by role (focus-block radius on the brand icon, card radius on form containers, control radius on inputs/buttons), motion tokens on all transitions, functional copy with no AI writing tells.

**Multi-Tenant Architecture Transition (2026-08-08):**
- Transitioned the single-tenant setup to a multi-tenant shared database architecture via PostgreSQL Row Level Security (RLS).
- Introduced a mandatory `business_id` column on all primary tables, populated automatically or safely via `auth_business_id()` resolving the tenant dynamically based on the signed-in user (`users` table).
- Implemented a secure registration trigger (`handle_new_owner`) that seamlessly provisions a new `business_profile` and links the new owner to it, utilizing metadata passed during `supabase.auth.signUp()`.
- Updated all edge functions (like `manage-staff`) and synchronization procedures (`sync_apply_*`) to strictly pass and enforce `business_id` scoping to prevent tenant data leakage.

**Auth Flow Enhancements (2026-08-08):**
- Replaced the single-step email/password registration with an inline 3-step OTP flow (`signUp()` -> `verifyOtp()` -> set PIN) to ensure immediate email verification before allowing offline access.
- Added Google OAuth support (`signInWithOAuth`) to both `/login` and `/register`.
- Implemented `src/app/register/callback/page.tsx` using `@supabase/ssr` to handle the PKCE code exchange securely on the server and safely configure the `business_profile`.
- Introduced `EmailVerificationBanner.tsx` allowing existing unverified sessions to complete OTP verification via Supabase Edge Functions.

**UI Performance and Validation Polish (2026-08-08):**
- Replaced basic opacity fade (`animate-pulse`) with hardware-accelerated sweeping CSS gradients (`animate-shimmer` via `transform: translateX`) to optimize skeleton loader performance on low-end devices without triggering CPU repaints.
- Created `loading.tsx` layout boundaries for all 9 primary route segments (Dashboard, POS, Products, Reports, Settings, Sales, Customers, Staff, Purchases) to guarantee instant screen transitions.
- Standardized form validation error behavior by introducing `useScrollToError`, a custom hook wired to all authentication and setup forms, ensuring users are smoothly scrolled back to the top to see context-aware error banners.
